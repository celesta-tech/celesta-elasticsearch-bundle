# CLS-5072 — {C} [elasticsearch-bundle] OpenSearch - run the bundle on OpenSearch

Branch `CLS-5072` starts from `master` (`11d8c9b`, v1.6), and the PR targets `master`. Merging it releases v1.7 through `.github/workflows/release.yml`. ## Overview

CLS-541 moves crm and segment to the newest OpenSearch that AWS OpenSearch Service offers, and runs the CI test containers on the same version. Today the bundle's CI starts one search service, `docker.elastic.co/elasticsearch/elasticsearch:7.10.2`, and the functional tests reach it at `ELASTICSEARCH_HOST`. segment ships the bundle (`^1.5`, locked at v1.5) to every environment, and some environments still run Elasticsearch 7.10 while others move. So the bundle has to keep working on both engines.

The bundle needs no library change. `master` passes its whole suite on OpenSearch 3.7.0 with 100% coverage, using `elasticsearch/elasticsearch` 7.17 as the sub-task decided.

This change does four things:
- runs CI against OpenSearch 3.7.0 and Elasticsearch 7.10.2, one matrix leg each, both with the 100% coverage gate
- adds a functional test proving that a released scroll result frees its scroll on the engine
- updates `CLAUDE.md` for OpenSearch, the two-engine CI, and segment's real constraint and lock

## Architecture & Design

**Version.** `opensearchproject/opensearch:3.7.0`. AWS OpenSearch Service added 3.6 and 3.7 on 2026-07-29 ("Support for OpenSearch 3.7" in its release notes). 3.7.0 is the only 3.7 image on Docker Hub. The domains CLS-3328 creates are to run 3.7, and crm (CLS-3325), segment (CLS-3326) and the local container (CLS-3327) use the same version.

**Dry run, 2026-11-16.** Run on a scratch copy of `master` with task 3's test added, on `cls3891-php84` (PHP 8.4.27 with pcov), with each engine started from the single env block below.

| Engine | Result |
|---|---|
| OpenSearch 3.7.0 | OK (152 tests, 365 assertions); classes, methods, lines 100% |
| Elasticsearch 7.10.2 | OK (152 tests, 365 assertions); 100% |
| OpenSearch 3.5.0 (also, before the version was settled) | OK (152 tests, 365 assertions); 100% |

`master` alone, without the new test, also passed on OpenSearch 3.5.0: 151 tests, 100%.

**What was checked on the engines.** All of these were observed on both OpenSearch and Elasticsearch 7.10.2:
- The `flush_synced` commit mode (`IndexService::commit()` → `indices()->flushSynced()` → `POST /_flush/synced`) still answers 200 on OpenSearch, so `IndexService` keeps it.
- A scroll keeps the same `_scroll_id` across pages.
- `clearScroll` frees the context (`num_freed: 1`).
- Scrolling a cleared id throws `Elasticsearch\Common\Exceptions\Missing404Exception`.

**CI: one job, a two-engine matrix.** The `tests` job of `.github/workflows/ci.yml` gets this `strategy`:
- `fail-fast: false`, so one engine's failure doesn't cancel the other's run
- a `search` matrix of the two images

Its service is renamed from `elasticsearch` to `search`, and its image comes from the matrix. Both engines start from one env block:

```yaml
    strategy:
      fail-fast: false
      matrix:
        search:
          - docker.elastic.co/elasticsearch/elasticsearch:7.10.2
          - opensearchproject/opensearch:3.7.0
    services:
      search:
        image: ${{ matrix.search }}
        env:
          discovery.type: single-node
          DISABLE_SECURITY_PLUGIN: "true"
          DISABLE_INSTALL_DEMO_CONFIG: "true"
          ES_JAVA_OPTS: "-Xms512m -Xmx512m"
          OPENSEARCH_JAVA_OPTS: "-Xms512m -Xmx512m"
        ports:
          - 9200:9200
```

Why this env block works for both:
- `xpack.security.enabled` is dropped. OpenSearch refuses to start with it (`unknown setting [xpack.security.enabled]`, observed on 3.5.0).
- Elasticsearch 7.10.2 serves plain HTTP without that setting, as observed in the dry run.
- Each engine ignores the other's uppercase variables.

The other steps stay as they are:
- The "Wait for Elasticsearch" step becomes "Wait for the search engine"; its command is unchanged.
- The PHPUnit step keeps `ELASTICSEARCH_HOST: localhost:9200`, which `Tests/app/config/config_test.yml` reads.
- The coverage step runs in each leg.

The `release` job is unchanged. Its `needs: tests` reads the matrix's combined result, which is `success` only when both legs pass.

**The scroll test.** `testScrollingSearch` already proves that a search scrolled one document per page returns all three documents. The new test proves the second half of the split's check against the engine itself:
- it releases the result
- `AbstractResultsIterator::__destruct()` then calls `IndexService::clearScroll()`
- the scroll id is therefore unknown to the engine afterwards

Today that is only checked against a mock, in `Tests/Unit/Result/AbstractResultsIteratorTest::testClearScroll`. Because the scroll id is stable across pages, the first page's `_scroll_id` (`getRaw()['_scroll_id']`) is the id the destructor clears.

**Library code: unchanged.** No class under `Service/`, `Result/`, `Mapping/`, `Command/` or `DependencyInjection/` changes. `composer.json` keeps `elasticsearch/elasticsearch ^7.17.2` and `handcraftedinthealps/elasticsearch-dsl ^7.0`.

## Edge Cases & Error Handling

- **`xpack.security.enabled` in the service env.** OpenSearch exits at startup with `unknown setting [xpack.security.enabled]`, so the shared env must not carry it, nor any other `xpack.*` setting. `CLAUDE.md` says so (task 5).
- **One engine fails in CI.** With `fail-fast: false`, the other leg still finishes and reports. The combined `tests` result is then a failure, so the `release` job does not run.
- **Slow OpenSearch startup.** The wait step polls `/_cluster/health` until the engine answers, as it does for Elasticsearch today. It has no timeout, unchanged.
- **Synced flush.** OpenSearch still serves `POST /_flush/synced` (200 on 3.5.0 and 3.7.0), so `commit('flush_synced')` keeps working, and its test runs on both legs.
- **The scroll id the destructor clears.** It is the latest one the iterator received. Both engines keep the id stable across pages, so the test's first-page `_scroll_id` is the same id. If an engine ever rotates ids, the test fails at `expectException` rather than passing silently.
- **PHP 8.4 deprecation notices** (`BooleanRequestWrapper::performRequest`, inside `elasticsearch/elasticsearch`) print on both engines, as they do on `master` today. PHPUnit does not convert them, and they are not addressed here.
- **A different release number.** If another PR releases first, the merge tags v1.8 instead of v1.7. Nothing depends on the number.

## Decisions

- **Which OpenSearch version do CI and `CLAUDE.md` pin?** `opensearchproject/opensearch:3.7.0`, the newest version AWS OpenSearch Service supports (release notes: "Support for OpenSearch 3.7", 2026-07-29). Upstream's 3.9 is not offered on AWS. The answer was first 3.5.0, from AWS's out-of-date "Supported versions" page, and was corrected after the release notes were checked. · answered by Pedro Martins, 2026-11-16
- **How is Elasticsearch 7.10 kept covered once CI runs OpenSearch?** A CI matrix over both engines until no environment runs Elasticsearch 7.10, rather than OpenSearch-only CI with a local 7.10 run. This turns the sub-task's "switch the CI search service" into "add OpenSearch next to it". Removing the 7.10 leg is a follow-up (Dependencies). · answered by Pedro Martins, 2026-11-16
- **How is "a scroll over more than one page clears the scroll" proven?** By a functional test in `IndexServiceTest` that releases a scrolled result and expects `Missing404Exception` when scrolling its id, rather than by the existing unit test's mock. · answered by Pedro Martins, 2026-11-16
- **No library change.** `master` passes on OpenSearch 3.5.0 and 3.7.0 at 100%, and the synced-flush endpoint still answers 200. · decided in this plan, from the dry run
- **One service env for both engines, without `xpack.security.enabled`.** OpenSearch refuses the setting, and Elasticsearch 7.10.2 serves plain HTTP without it. · decided in this plan, from the dry run
- **The CI service is renamed `search` and `ELASTICSEARCH_HOST` keeps its name.** The service now runs either engine. The variable is read by `Tests/app/config/config_test.yml`, and CI reaches the service at `localhost:9200` whatever it is called. · decided in this plan
