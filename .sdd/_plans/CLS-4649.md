# CLS-4649 — Monolog 3 support

Branch `CLS-4649` starts from `master` (v1.4) and the PR targets `master`. Merging it releases v1.5 through `.github/workflows/release.yml`. The open questions were answered on 2026-11-04 (see Decisions). The change was dry-run during planning in a scratch copy of `master`, so the results below were observed, not estimated.

## Context

Every tag up to v1.4 requires `monolog/monolog ^1.24|^2.0`. An application that needs Monolog 3 cannot install the bundle; on Symfony 7 that means any application using `symfony/monolog-bridge` 7.x, which requires Monolog 3.

Two places in the bundle stand in the way:
- `composer.json` excludes Monolog 3.
- `Profiler/Handler/CollectionHandler::write(array $record): void` overrides `Monolog\Handler\AbstractProcessingHandler::write()`. Monolog 3 declares that method as `write(LogRecord $record): void`, so on Monolog 3 the class fails to load ("Declaration … must be compatible").

The handler is loaded whenever the bundle's `profiler` setting is on (it defaults to `kernel.debug`). `MappingPass` then gives each `IndexService` the `ongr.esb.tracer` logger, a `Monolog\Logger` with this handler pushed (`Resources/config/services.yml:36-43`), and `IndexService::getClient()` passes it to `ClientBuilder::setTracer()`.

`ElasticsearchProfiler` reads the collected records by array access: `$record['context']`, `$record['context']['duration']`, `['uri']`, `['method']` and `$record['message']`. Monolog 3's `Monolog\LogRecord` implements `ArrayAccess` for those keys, so the profiler needs no change.

## Overview

- `composer.json` allows `monolog/monolog ^1.24|^2.0|^3.0`.
- `CollectionHandler::write()` takes `array|LogRecord`. The union type is compatible with each Monolog version's declaration: `array` in Monolog 1 and 2, `LogRecord` in Monolog 3. The handler stores records as it receives them.
- A unit test pins the handler's contract: a record logged through a `Monolog\Logger` is collected and exposes `message` and `context` by array access, which is what the profiler reads.
- Nothing else changes: the bundle's API, configuration, services and the profiler output stay the same.

## Architecture & Design

**`Profiler/Handler/CollectionHandler.php`.** Import `Monolog\LogRecord`, and change the signature to `protected function write(array|LogRecord $record): void`; the body (`$this->records[] = $record;`) stays.
- PHP accepts the wider parameter type as a contravariant override of every Monolog version.
- On Monolog 1 and 2, `Monolog\LogRecord` may not exist. A class name in a union type is not autoloaded at declaration, so this is fine.
- `getRecords(): array` and `clearRecords()` are unchanged. On Monolog 3, `getRecords()` returns `LogRecord` objects.

**`ElasticsearchProfiler`: unchanged.**
- `handleRecords()` and `addQuery()` use only `$record['context']` and `$record['message']`, and `LogRecord::offsetExists()`/`offsetGet()` serve both.
- `!empty($record['context'])` gives the same result: an empty context array is empty on both forms.
- `addLogger(Logger $logger)` and `Logger::getHandlers()` keep their signatures in Monolog 3.

**`composer.json`.** `"monolog/monolog": "^1.24|^2.0|^3.0"`. No other requirement changes.
- Monolog 3 needs `psr/log ^2.0 || ^3.0`, and Monolog 1 needs `psr/log ~1.0`. `elasticsearch/elasticsearch` 7.x and Symfony 7 accept every one of those.
- The lock is gitignored, so nothing else is committed.

**Release.** CI's `release` job runs `release.yml` after `tests` pass on a push to `master`. It bumps the latest release's minor version: v1.4 → v1.5.

  - Inside `esb-php`: install git and unzip, `pecl install pcov && docker-php-ext-enable pcov`, and Composer.
  - Then `composer update --ignore-platform-reqs`. This is the resolution CI makes, and it should give `monolog/monolog` `dev-main` (3.x-dev).

## Edge Cases & Error Handling

- **Records are `LogRecord` objects on Monolog 3.** `getRecords()` returns whatever the handler received. The profiler, the only reader, uses array access, which `LogRecord` implements. The functional profiler tests check that on Monolog 3, and the new unit test checks it on every version installed.
- **Monolog 1 needs `psr/log` 1.** Composer resolves `psr/log` 1.1.4 with it. Symfony 7 and `elasticsearch/elasticsearch` 7 accept `psr/log` 1, 2 and 3.
- **CI tests only Monolog 3.** `minimum-stability: dev` and the gitignored lock make CI install the newest allowed versions. Monolog 1 and 2 are checked by task 6's local runs, recorded in the PR (Decisions).
- **A different release number.** If another PR releases before this one, the merge tags v1.6 instead of v1.5. A `^1.5` constraint accepts either.
- **Installing the branch before the tag.** A consumer that pins `dev-CLS-4649` before v1.5 exists needs the branch to stay until it has moved to the tag, so keep the branch until then.

## Decisions

- **Monolog range `^1.24|^2.0|^3.0`**, keeping Monolog 1 rather than dropping it (`^2.0|^3.0`) or allowing Monolog 3 only. It needs no extra code, all three versions pass the suite, and the release removes nothing v1.4 accepted. · answered by Pedro Martins, 2026-11-04
- **Monolog 1 and 2 are checked by a local run recorded in the PR**, rather than a CI job pinned to them; `.github/workflows/ci.yml` does not change. · answered by Pedro Martins, 2026-11-04
- **The handler stores records as received**, rather than converting `LogRecord` to arrays, because the profiler's array access works on both. · decided in this plan
- **A unit test for `CollectionHandler`**, so the handler's contract is checked without Elasticsearch on whichever Monolog is installed. · decided in this plan
